## Systems engineering (NASA-derived 17 processes) (`systems-engineering`)

Sources: `nasa-se` (INACCESSIBLE), `nasa-se-design` (INACCESSIBLE), `nasa-se-realize` (INACCESSIBLE), `nasa-se-manage` (INACCESSIBLE)  
Agents: `systems-engineer`, `requirements-engineer`, `systems-architect`, `vv-engineer`, `safety-risk-reviewer`

| Skill | Use when |
|---|---|
| `se-stakeholder-conops` | Define stakeholder expectations and a concept of operations (mission need, stakeholders and decision rights, nominal and off-nominal scenarios, modes, environment, constraints, measures of effectiveness, assumptions) with evidence-tagged needs. Use at the start of an engineering project or new phase, before writing requirements, when the problem or users are unclear, or when reviewing a ConOps for solution bias, missing failure scenarios or invented stakeholder claims. |
| `se-requirements` | Draft, lint and baseline traceable technical requirements (shall-statements with rationale, owner, verification method and measurable acceptance criteria) and manage them under change. Use when turning stakeholder needs or a ConOps into system/subsystem/software requirements, reviewing a requirements register for ambiguity, atomicity, TBDs, orphans or broken parent links, or preparing an SRR-style baseline. |
| `se-logical-decomposition` | Decompose system requirements into a functional architecture (verb-object function tree with inputs/outputs), allocate leaf functions to physical or software elements, and check data-flow closure and requirement coverage. Use after system requirements and before architecture trades or interface definition, when building a function tree or functional flow, or when checking that every requirement is realised by some function and every function by some element. |
| `se-architecture-trades` | Define design solutions by generating a morphological trade space of concept options per function, screening combinations with compatibility and maturity (TRL) rules, then evaluating survivors with decision analysis and recording the selected concept with a requirement compliance view. Use when choosing a system or subsystem architecture, comparing build/buy/reuse concepts, or documenting why a design concept was selected before preliminary design. |
| `se-implementation-integration` | Plan product implementation (make, buy, reuse, with unit-level verification) and an incremental integration sequence in which every step has prerequisites, checks and interface coverage; detect assemblies used before they exist, cycles, unverified components and untested interfaces. Use when planning how components become a working system, preparing an integration plan or test-bed, or reviewing whether an integration sequence is ready to execute. |
| `se-verification-validation` | Plan and audit product verification (did we build it right — against each requirement) and validation (did we build the right thing — against stakeholder needs) with a traceable V&V matrix, objective acceptance criteria and evidence records. Use when writing a verification matrix or test/validation plan, assessing coverage before a TRR/acceptance review, or checking claimed test results for missing evidence, configuration or independent review. |
| `se-transition` | Prepare and check a product transition package — deliverables with versions, configuration IDs and acceptance records, documentation, known limitations, waivers for any open verification, training, support, handling and storage — so the receiving organisation can accept the product knowingly. Use when handing a prototype, system, data set or software release to a user, operator, customer or the next project phase. |
| `se-technical-planning` | Tailor a proportionate systems-engineering approach to a project's risk, safety, regulatory and novelty profile — rigour per process, artifacts, milestone reviews and named decision authorities — and draft the engineering plan (milestones, work breakdown, responsibility matrix, baselines, reserves). Use at project start or phase change, when deciding how much process a project needs, or when nobody knows who approves baselines, risk acceptance or physical tests. |
| `se-interface-control` | Define, baseline and check system interfaces (mechanical, electrical, data, software, thermal, operational, human) in an interface control register with owners on both sides, units, ranges/protocols, failure behaviour and verification links; produce an N-squared matrix. Use when drafting an ICD, integrating subsystems or suppliers, reviewing interface readiness before PDR/CDR/integration, or detecting unit mismatches and unowned interfaces. |
| `se-risk-analysis` | Identify, score, handle and track technical, safety, cost and schedule risks with a policy-driven likelihood x consequence register and FMEA worksheets, including residual risk and human risk acceptance. Use when building or reviewing a risk register, running an FMEA on a design, preparing risk content for a design review, or checking that high risks have owners, mitigations, triggers and authorised acceptance. |
| `se-configuration-management` | Identify configuration items, establish versioned baselines, account for their status and audit that every difference between baselines is backed by an approved change request (no deletions instead of retirement, no reused retired IDs, no changes under rejected CRs). Use when setting up configuration control for a project, cutting a new baseline, preparing a configuration audit, or checking that requirements/ICD/risk registers changed only through approved changes. |
| `se-change-control` | Assess a proposed change to a baselined requirement, interface or design item by tracing its impact through derived requirements, verification evidence, interfaces and risks, then preparing a change request for an owner or change-board decision. Use when someone wants to modify an approved requirement, an agreed interface or a tested configuration, when evidence may have been invalidated by a change, or when preparing a change request. |
| `se-technical-data-management` | Plan and audit how technical data (requirements, models, drawings, test data, reviews, records) is identified, owned, classified, stored, access-controlled, retained and kept as a single source of truth, including personal-data and export-control flags and credential hygiene. Use when setting up project data storage, onboarding a team, preparing for an audit or transition, or checking a data register for missing owners, conflicting copies, embedded credentials or unbounded retention. |
| `se-technical-assessment` | Assess technical progress against plans using technical performance measures (TPMs) with limits, alert margins and trend projections, plus measures of effectiveness/performance and progress reviews. Use when tracking mass, power, latency, accuracy, cost-to-complete or similar key parameters over time, preparing a technical status or design review, or deciding whether a parameter trending toward its limit needs corrective action. |
| `se-decision-analysis` | Structure and document consequential technical or programme decisions with explicit alternatives, must-criteria screens, weighted criteria, evidence-tagged scores, weight sensitivity and switching weights, ending in a recommendation for a named human decision owner and a decision-log entry. Use for trade studies, make/buy/reuse choices, technology or supplier selection, or whenever a decision needs a defensible, reviewable rationale. |
| `se-review-gates` | Prepare and run evidence-based milestone reviews (concept, requirements, system definition, preliminary/critical design, test readiness, acceptance, operational readiness) by checking criteria against recorded evidence, automated check results and open actions, then producing a GO / GO_WITH_CONDITIONS / NO_GO recommendation for a named human gate authority. Use when assembling a review package, chairing or simulating an independent review, or deciding whether a project is ready to pass a gate. |

## Space engineering supplements (`space-engineering`)

Sources: `ecss-se` (INACCESSIBLE), `nasa-se` (INACCESSIBLE)  
Agents: `systems-architect`

| Skill | Use when |
|---|---|
| `space-technical-budgets` | Build and check spacecraft/robot engineering budgets (mass, power, energy per mode, data volume, link margin, pointing/timing) with explicit allocations, current best estimates, maturity-based contingency and system margin against a programme-supplied margin policy, plus TPM trend tracking and radio link budgets (FSPL, EIRP, G/T, Eb/N0). Use when preparing or reviewing a mass/power/data/link budget, setting or auditing contingency and margin, tracking technical performance measures across design iterations, or checking a link closes before a design review. |
| `space-low-gravity-mobility` | First-order physics and procedure for robot surface mobility on small bodies (asteroids, comets, small moons) — surface gravity, escape and orbital speed, ballistic hop time/range/apex, take-off impulse and traction limits, bounce settling with coefficient of restitution, rotation (centrifugal) effects — plus planning of terrestrial low-gravity test analogues. Use when sizing hopping, wheeled or legged locomotion for a low-gravity body, checking a hop or bounce stays well below escape speed, assessing fast-rotator surface conditions, or planning offload-rig, drop-tower, parabolic-flight or air-bearing tests (e.g. Project ASTER asteroid-mining robot). |

## Reliability and security (`reliability-security`)

Sources: `owasp-asvs` (VERIFIED), `nist-ssdf` (PARTIALLY_VERIFIED), `google-sre` (INACCESSIBLE)  
Agents: `security-reviewer`, `reliability-engineer`

| Skill | Use when |
|---|---|
| `security-threat-model` | Build and check a STRIDE-style data-flow threat model - components, assets, trust boundaries, boundary-crossing data flows, threats rated by likelihood and impact, and mitigations mapped to version-prefixed OWASP ASVS 5.0.0 requirement IDs - including tenant-isolation threats for multi-tenant SaaS. Use when designing or changing a system's architecture, adding an external integration (LLM provider, webhooks, payment), preparing a security design review, or checking that every trust-boundary crossing has analysed threats and that cited ASVS IDs exist. |
| `security-asvs-controls` | Choose an OWASP ASVS 5.0.0 verification level (L1/L2/L3) and chapters for an application, build a control verification map (asvs_id, level, applicability with justification, implementation, verification method, evidence, status) and compute verification coverage with version-qualified ID validation. Use when planning application security verification, scoping a penetration test or security review against ASVS, tracking which ASVS requirements are verified with evidence, or checking a map for unknown IDs, unjustified N/A rows or passes without evidence. |
| `security-code-checks` | Run a lightweight, explainable heuristic security screen over Python, JavaScript, TypeScript and SQL files - hard-coded secrets, SQL built by string formatting, queries on tenant-scoped tables missing the tenant filter, debug mode, MD5/SHA-1 password hashing, unsafe deserialisation (pickle, yaml.load), disabled TLS verification, wildcard CORS with credentials and JWT 'none'/unverified tokens - each mapped to an OWASP ASVS 5.0.0 chapter or section. Use when pre-screening a change or repository before human security review, checking a multi-tenant codebase for missing tenant filters, or teaching common insecure patterns; not a SAST tool. |
| `security-secure-development` | Map an organisation's secure software development evidence to NIST SSDF (SP 800-218 v1.1) practices and tasks, check practice/task IDs, evidence presence and freshness, coverage per group (PO, PS, PW, RV), and check dependency manifests (requirements.txt, package.json, pyproject.toml) for unpinned or range-specified versions and missing lockfiles. Use when preparing for a customer or supplier secure-development questionnaire, building an SSDF evidence register, auditing evidence age, or tightening dependency pinning as a supply-chain control. |
| `sre-service-level-objectives` | Define, check and operate service level objectives - user-journey SLIs from good/valid events, targets, windows, error budgets (allowed bad minutes/events), budget consumed and remaining, burn rates and multi-window multi-burn-rate alert evaluation - plus an SLO specification validator (journey, SLI definition, target, window, owner, exclusion, alerting and error-budget policies). Use when setting or reviewing an SLO, computing an error budget (e.g. 99.9% over 30 days = 43.2 minutes), designing or testing burn-rate alerts, or deciding whether to slow releases because the budget is spent. |
| `sre-incident-response` | Run and learn from production incidents - classify severity, assign incident roles (incident commander, operations lead, communications lead, scribe), keep a communication cadence, stabilise first, then write and check a blameless postmortem (summary, quantified impact, ordered UTC timeline, root causes and contributing factors, detection, response, what went well/badly, owned and tracked action items). Use when an incident is declared or suspected, when drafting or reviewing a postmortem, or when checking that postmortem action items have owners, priorities, due dates and tracking IDs. |
| `sre-production-readiness` | Run a production or launch readiness review covering SLOs, monitoring, alerting, capacity, dependencies, rollback, runbooks, on-call, security sign-off, backup/restore testing and feature flags, with evidence references per item, and produce a GO / GO_WITH_CONDITIONS / NO_GO recommendation where no tested rollback, no staffed on-call, no SLO or an untested restore always block. Use before launching a new service or major feature, before moving a beta to general availability, or when auditing whether a service is still fit to run in production. |

## Product management (`product`)

| Skill | Use when |
|---|---|
| `product-discovery` | Run evidence-led product discovery - separate observed evidence from hypotheses, register risky assumptions, audit the evidence log for fabricated quotes and untraceable claims, and recommend a discovery-to-alpha (or alpha-to-build) phase gate. Use when exploring a customer problem, validating a concept or MVP, preparing a discovery report, or challenging "users want X" claims before committing to build. |
| `product-experiment-design` | Design, size and evaluate product A/B experiments on conversion-type metrics - falsifiable hypothesis, one primary metric, baseline, minimum detectable effect, alpha/power sample size, duration, stopping rule, guardrails, ethics note and a decision rule fixed before launch; then evaluate results with a two-proportion z-test and confidence interval.
